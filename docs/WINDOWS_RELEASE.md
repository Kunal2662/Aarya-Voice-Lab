# Windows Release Preparation

Task 6 of the Phase 4 autonomous execution plan. This document and
[`aarya_voice_lab.release`](../src/aarya_voice_lab/release.py) prepare
repository-safe groundwork for a future Windows release. **No installer
binary is generated, signed, or shipped by this work**, and nothing here
modifies AARYA Core, which remains a separate, out-of-scope system.

## Release configuration

[`configs/release.yaml`](../configs/release.yaml) is the single source
of release/packaging metadata, loaded via
`aarya_voice_lab.release.load_release_metadata()` — the same
`yaml.safe_load` + required-keys pattern `core.config.load_config()`
already uses for `configs/default.yaml`. It carries:

- **Version metadata**: `product_name`, `version`, `schema_version`,
  `publisher` — a future installer's product/version fields would read
  directly from here, never a second, independently-maintained copy.
- **Installer metadata**: `platform`, `min_os_version`, `architecture`
  — descriptive facts a WiX/Inno-Setup-style manifest would need. No
  such manifest is generated by this task; these are the facts one
  would consume.
- **Runtime packaging layout**: `data_directories` — the exact set of
  top-level directories a fresh install must have present and writable,
  mirrored from
  [`core.paths.PROTECTED_DIRECTORIES`](../src/aarya_voice_lab/core/paths.py)
  (kept in sync by test, the same discipline `configs/default.yaml`'s
  own `protected_directories` list already follows).

## Directory layout

Every directory a release needs already exists in this repository's own
layout, git-ignored with only a `README.md` tracked (`source/`,
`datasets/`, `public_datasets/`, `models/`, `experiments/`,
`benchmarks/`, `reports/`, `logs/`, `manifests/`, `data/`). A Windows
release does not introduce new directories; it inherits this exact
layout. `aarya_voice_lab.release.validate_release_layout()` checks that
every declared directory exists and is writable — a read-only readiness
check, never a directory-creation side effect (creating one is a
separate, explicit first-run step this task does not implement).

## Migration layout

Every persisted record in this project already carries a
`schema_version` field (segment, dataset manifest, experiment, model
registry, training job, public dataset registry, voice package manifest
— every schema under `schemas/`). This is the migration mechanism: a
future release that changes a schema's shape bumps `SCHEMA_VERSION`
(see `aarya_voice_lab.__init__`'s own docstring: "Bump when a schema's
shape changes incompatibly"). `aarya_voice_lab.release.check_schema_compatibility()`
compares an installed checkout's recorded schema version against the
running code's, by major version only (matching semver's own
compatibility convention) — a major mismatch is refused rather than
silently read, exactly the same fail-closed discipline
`pipeline.dataset_gate` and `pipeline.public_dataset_gate` already
apply elsewhere in this project. No actual migration *procedure*
(rewriting old records to a new shape) is implemented by this task —
that is real, schema-specific work for whenever a breaking schema
change is actually made, not something to build speculatively now.

## Uninstall safety

**An uninstaller must never delete `source/`, `data/`, `models/`, or
`public_datasets/` without a separate, explicit user confirmation
beyond "uninstall this program."** These directories may contain real
recordings, biometric embeddings, or trained models — the exact
material [`PRIVACY.md`](PRIVACY.md) already protects. `configs/release.yaml`'s
`uninstall_protected_directories` names them explicitly, and
`aarya_voice_lab.release.is_safe_to_delete_without_confirmation()` fails
closed: an unrecognised directory name is also treated as unsafe, never
assumed removable.

Directories that are always safe to remove on uninstall without
additional confirmation: `logs/`, `reports/`, `benchmarks/`,
`experiments/` — working output with no biometric or private-recording
content, reconstructible by re-running the pipeline.

## What this task does not do

- Does not generate a `.msi`, `.exe` installer, or any installer
  binary.
- Does not implement a real migration procedure for any schema — only
  the compatibility *check*.
- Does not change how `core.paths.PROJECT_ROOT` is resolved (still the
  nearest ancestor directory containing `pyproject.toml`) — a fully
  relocatable, non-dev-checkout installation layout is a larger,
  separate architectural decision this task does not make on its own.
- Does not touch AARYA Core in any way.
